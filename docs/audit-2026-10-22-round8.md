## 4. 发现完整论证

### F-103 分享枚举闸未覆盖全部匿名端点（Medium，已修）

- 证据：修复前 `FileShareEndpoints.GetPublicShareInfo` 在 handler 内调用 `ShareEnumerationGuard.TryAcquire()`，而 `download`、`download/{subPath}`、`files`、`files/{subPath}`、`verify` 五条匿名路由没有全局闸，只有组级的按 IP 窗口。当前在 `MapPublicShareEndpoints` 的组上挂 `AddEndpointFilter`，统一计数（`FileShareEndpoints.cs` 组创建处），info handler 内的检查已删除。
- 机理：分享码存在性不只经 info 端点泄漏。未知码在 download/files 返回 404，已存在但需口令的分享返回 400/401，攻击者同样能区分。按 IP 窗口只限制单来源，分布式来源可把探测速率摊到大量 IP 上；全局闸是第二层总速率，缺了它，攻击者可以绕开 info 直接打 download。
- 触发条件：分布式来源对 `/api/v1/public-shares/{code}/download` 等路径枚举分享码。
- 最坏影响：全局探测速率上限形同虚设，枚举速度回到按 IP 窗口能承受的上限；分享码空间 31^6 很大，实际风险是"比预期快"，不是"立刻可枚举完"。定 Medium。
- 现有测试为何没拦住：`ShareEnumerationRateLimitTests` 只测 info 端点的全局闸；`ShareHardeningRegressionTests` 测下载上限与口令，没有跨端点的枚举闸用例。
- 自我反驳：组级 `RequireRateLimiting("share")` 不是已经覆盖所有端点了吗？它按 IP 分区，对单来源有效，对分布式来源无效，这正是 F-073 引入全局闸的原因。把全局闸挂到整组会不会误伤正常浏览器？全局阈值默认 600/分钟，一个链接被几十人同时打开远到不了；组级按 IP 窗口仍在，两层叠加。
- 最小修复：组级 endpoint filter 统一 `TryAcquire`，超限 429；info handler 去掉重复检查。新增匿名端点自动继承，不会再漏挂。
- 验证方式：新增 `ShareEnumerationGuardTests`，用独立工厂把 `ShareGlobalPerMinute` 配成 1，连续两次请求 `download` 未知码，断言第一次 404、第二次 429。S3 移除 filter 后，新用例与既有 `ShareEnumerationRateLimitTests` 同时转红（2 failed），恢复后全绿。
- 回归风险：所有匿名分享请求共享一个总速率；阈值可按配置调整。测试环境 `SharePerMinute` 默认 int.Max，不受按 IP 窗口干扰。
- 静默控制问句：如果 filter 没挂上，第二次 download 仍是 404，用例断言 429 失败。

### F-104 数据库/磁盘依赖故障落 500（Low，已修）

- 证据：`GlobalExceptionHandler` 原只转译唯一约束、参数绑定、取消等，`SqliteException`（锁库/只读/不可打开/写满）与 OS 级 `IOException` 都落默认 500。当前 `:81` 起新增三条分支：SQLite 5/8/14 回 503，SQLite 13 回 507，磁盘满 IOException 回 507。
- 机理：依赖暂时不可用（锁库、只读、文件打不开）与请求本身的错误不同，也不是内部 bug。回 500 会让客户端与告警把"稍后重试即可"当成"服务端故障"；磁盘满则应回 507，与配额/容量错误的语义一致。SQLite 在全盘写满时抛 `SQLITE_FULL`（13），OS 写入则可能先抛 `IOException`（Windows ERROR_DISK_FULL 0x80070070 / ERROR_HANDLE_DISK_FULL 0x80070027，Unix ENOSPC HResult 28）。
- 触发条件：另一个进程长时间持写锁、数据卷被改成只读、数据盘或临时盘写满。
- 最坏影响：错误状态与文案误导排障；客户端可能立即重试放大压力，或把可恢复故障报成不可恢复。不丢数据；上传临时文件清理与版本孤儿补偿已在既有实现。
- 现有测试为何没拦住：异常映射测试只覆盖参数绑定、InvalidOperationException 与 FileNotFoundException，没有数据库/磁盘依赖故障。
- 自我反驳：真实只读库与磁盘满沙箱没有跑。本机无 Docker、无法安全造小卷；用 `PRAGMA query_only` 或只读文件属性模拟 SQLite 的异常码需要额外环境，未执行。因此本轮只锁"异常到达中间件后的映射"，不宣称端到端故障注入已验证；异常码取值来自 SQLite 与 Windows/Unix 的公开错误码定义。另一个边界：只读库的连接与 `SELECT 1` 可能成功，F-102 的健康检查覆盖不到只读（第 7 轮已写明），这两条合起来意味着"只读库"仍主要靠写入错误暴露，但至少现在状态码是 503 而不是 500。
- 最小修复：三条异常分支 + 磁盘满判定助手；不改变成功路径。
- 验证方式：`GlobalExceptionHandlerTests` 三例（SQLite 只读 8 回 503 且码为 Error.DatabaseUnavailable、SQLite 满 13 回 507、IOException 磁盘满回 507）。S3 关闭三条分支后三例转红。
- 回归风险：`IOException` 只在命中磁盘满错误码时映射 507，其他 IO 故障仍走默认 500；不会把普通 IO 错误误报成容量问题。
- 静默控制问句：如果分支被移除，三例分别拿到 500，状态断言失败。
