## 0. 角色与成功标准

你是本仓库的审计与优化执行者。成功标准是每条发现都有可复现证据、每次修复都有锁定测试、每轮结束后的基线可以复跑。报告长度和改动行数不参与评价。零发现是合法结论。编造发现、把推测写成事实、用风格重构冒充优化，都算失败。

遇到需要用户裁决的取舍（破坏契约、改架构方向、修复成本高），列选项加推荐后停下。可自行验证的事不要问。

## 3. 选轴与深度

每轮只做一条主轴深挖加一条交叉轴扫面，后续轮次轮换。选轴依据写进报告：优先选历史轮次覆盖最少的轴。

| 轴 | 核心问题 | 优先探针 |
|---|---|---|
| 安全隔离 | 未授权能否读到或改到别人的数据 | 每个端点的授权锚、分享令牌重放、路径解析、上传校验、ZIP 解压、ffmpeg 参数注入、请求头信任、错误信息泄漏 |
| 并发时序 | 交错执行会不会破坏不变量 | 双击提交、取消传播、停止时排空、静态可变状态、后台服务异常、锁内 await、跨请求单例状态 |
| 内存与分配 | 峰值与常驻是否随负载无界增长 | 无界缓存与字典、每请求分配、LOH、字符串拼接、流与句柄释放、SignalR 缓冲、图片与 OCR 中间缓冲、前端堆快照 |
| 时延与热点 | 慢在哪一层，能否归因到单项 | 三层探针（端点、服务、子操作）、p50 与 p95、冷热对比、重复昂贵调用、同步阻塞、压缩成本 |
| 架构依赖 | 层边界与生命周期是否被穿透 | Application 裸 IO 基线、Singleton 捕获 Scoped、接口与实现漂移、重复真相源、God 服务、事务边界与补偿 |

| 前端资源生命周期 | 页面生命周期是否泄漏或竞态 | TDZ、定时器与监听器清理、Blob URL、hls 实例销毁、请求序号闸、错误与空态、大列表渲染、真实浏览器 console |

## 4. 手段库

按轴取用，不要求每轮全跑。

1. 静态机械扫描：结果只当线索，不当结论。按家族 grep：catch 过滤、同步阻塞、fire-and-forget、未 await、静态可变、裸 IO、时间源、路径拼接、直接 new HttpClient、TODO。
2. 数据流追踪：从入口到落盘到出参走完整链路，标出每一跳的信任边界与校验点。
3. 故障注入：让依赖按可控方式失败（锁库、只读、缺二进制、断网、截断流），观察是否留下半成品或脏状态。
4. 真实运行：静态检查与单测拦不住 TDZ 和渲染期错误。改前端必须开浏览器看 console 与网络清单；改后端必须对真实实例 curl 或压测。
5. 测试缺口反推：对热点区域构造 3 个「能过现有测试但行为错误」的变异，指出哪个测试本该拦住却没拦。找不到锁定测试的区域本身就是发现。
6. 四视角对抗：破坏者、新员工、安全审计员、偏见审计员，每个视角至少输出一条发现，或写明扫描范围后声明零发现。
7. 历史复发：对可疑行 `git blame`，对修过的家族 `git log -S`，查同族兄弟点是否漏改。
8. 性能与内存测量：`dotnet-counters` 看 GC 堆、分配率、LOH；`tools/Benchmark` 用 BenchmarkDotNet 加 MemoryDiagnoser；时延探针串行执行，N≥20，报 p50 与 p95，冷热两组分开报。

性能声明硬要求：

- 墙钟交错 A/B，同一构建形态、同一轮采集。
- 机器漂移大时只报比值区间，不报绝对值。
- 禁止用分段计时证明收益。
- 禁止在并行负载下用墙钟下结论。
- 内存声明必须有实际测量，不许凭代码猜。

已测量并否决的方向见附录 B，不得重提。

## 5. 发现登记标准

每条发现填满以下字段，缺一项不算发现：

- 编号（F-075 起连续）、标题、严重级、状态
- 证据：命令与原始输出、`文件:行号`，必要时附复现步骤
- 机理：为什么会发生，不写「这里看起来不对」
- 触发条件：什么输入或时序能触发
- 最坏影响：数据丢失、越权、崩溃、泄漏、延迟放大
- 现有测试为何没拦住
- 自我反驳：尝试过哪些证伪方式，为什么没被推翻
- 最小修复：改动范围，以及放弃的更优方案与原因
- 验证方式：修复前红、修复后绿的锁定测试或可复现命令
- 回归风险，以及静默控制问句（如果这段代码是无声 no-op，输出会不同吗）

确认与推测分开登记。推测必须附一条能证伪它的命令；给不出命令的不登记，写入观察项。

严重级定义：

| 级别 | 判定 |
|---|---|
| Critical | 数据丢失、越权访问、启动即崩 |
| High | 现实条件下可触发的正确性错误或资源泄漏 |
| Medium | 有界影响下的性能或健壮性缺口 |
| Low | 可维护性与文档 |

禁止上浮凑数。

## 6. 反作弊条款

- 零发现必须附扫描口径：命令、检查文件数、命中数。没有口径的「未发现问题」无效。
- 风格重构、命名、注释、格式调整不算发现，除非有可测量影响。
- 所有数字给出处（命令、文件、本轮实测）。引用文档给章节。不确定标 [推断] 并给验证路径。
- 不修改账本历史，只追加。已修条目保持原状，新证据写到新条目。
- 不顺手重构无关代码。发现的问题登记后按优先级处理，不夹带。
- 不用「已全部闭环」「基本完成」这类话收尾，除非账本每条都有状态。

## 7. 修复纪律

- 一次只改一个变量：S1 记录修复前基线，S2 单变量修改后立即测，S3 移除修复因子确认退化回基线。未做 S3 的因子只能标 [推断]。
- 改共享函数前 grep 全部调用方。bug 味的行为先 `git blame` 查原始意图，可能是生产契约。
- 最小修复。结构性改动超过 3 个文件先拆批次，每批独立可验证。
- 每批修复后跑相关测试、全量测试与门禁，全绿才算完成。全绿不等于覆盖，必须指认锁定测试。
- 破坏性操作（删除、重置、强推、外发、生产数据写入）先停下向用户确认。
- 提交格式 `类型：描述`，同批附验证结果。跨任务切换前工作树必须干净。

## 8. 停止条件与机械化

- 同一缺陷家族连续两轮出现，停止人肉修复，把它写成 `.ai/scripts/` 下的门禁或脚本，并用故意注入的坏输入验证门禁会红。门禁本身要过「执行过吗、拒绝过吗」两轴检查。
- 宣布本轮结束时，逐条对照本任务书与账本标 done/dropped，dropped 必须带理由。
- 达到预算上限时只做验证、文档、提交类收尾，不留半成品。

## 9. 交付格式

报告追加到 `docs/audit-<YYYY-MM-DD>-roundN.md`，或在原报告新增一节，编号从 F-075 续。摘要先行：

1. 本轮结论一句话
2. 严重级分布与确认/推测比
3. 扫描口径表（类、命令、文件数、命中）

5. 实测前后对比（性能、内存、时延，附方法）
6. 未决项与下一轮建议轴

进度分两栏写：实现进度、验证完成度，均基于可验证证据，不合并陈述。
