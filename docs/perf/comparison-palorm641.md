# 对比报告：PalORM 6.4.1 适配（D1 → D2 → D3）

## 一、报告定位

本文件是 PalORM 6.4.1 升级与适配的对比结论。基线（net10 + EF）见 `baseline.md`，
上一轮 PalORM 6.1.0 迁移见 `comparison.md`。三臂同机同种子数据，harness 与口径完全一致。

| 臂 | 内容 | 角色 |
|---|---|---|
| D1 | net11 + PalORM 6.1.0 + 原查询策略 | 上一轮迁移的终点 |
| D2 | net11 + PalORM 6.4.1 + 回归修复 + 原生枚举 | 隔离版本与修正的影响 |
| D3 | net11 + PalORM 6.4.1 + ConvertAll + schema 校验 + LIKE 修复 | 目标态 |

D1→D2 只换版本与修正，查询策略一行不动；D2→D3 只加 ConvertAll、启动校验与转义修复。
原始记录：D1 = `net11-palorm-20261011-{201157,201550,202058}`，
D2 = `net11-palorm-20261012-{023536,023952,024500}`，
D3 = `net11-palorm-20261012-{033936,034343,034853}`。

**D1→D2 是净收益**：数据层全面快 10% 到 15%，API 吞吐 +9.3%，无回归。

（源生成器新增 `ConvertDeleteKey` 委托，复用槽命中时不再走探针命令）。

**D2→D3 看起来是退化，实际是端点口径变了**：D2 测 7 个端点，D3 测 8 个
（补了 `/api/v1/public-shares/{code}`）。每轮多打一个端点，总请求数下降属预期，
不能直接比吞吐。同口径的 D3 内部对比见第四节，各端点与 D2 同口径时持平或略好。

## 五、本轮修的两个正确性缺陷（基准测不出来）

### 外键约束回归

影子行模型漏声明 `[ForeignKey]`，`MigrateAsync` 建出的新库外键数为 0，
而 EF 时代的 schema 有 7 个。存量库不受影响（表已存在，幂等建表不重建，旧约束还在），
但新建库删除父行不再被 RESTRICT 拦住。补 `[ForeignKey]` + `OnDelete` 后恢复 3+2+2=7。

### LIKE 转义失效

`EscapeLike` 生成"反斜杠+下划线"，但 SQLite 的 LIKE **没有默认转义字符**，
该序列被解释成"反斜杠 + 任意单字符"，导致搜 `rep_ort` 返回 0 条
（不转义则会多匹配 `repXort`，两个方向都错）。修法是每个 LIKE 配 `ESCAPE` 子句，
转义字符选 `#` 而非反斜杠：反斜杠在 C# 字符串里本身要转义，多层嵌套极易写成
运行期是空字符的 `ESCAPE ''`，那种错法 SQLite 直接报语法错误；
`#` 在 C# 字符串里无需转义，写出来就是运行期的样子。

两个缺陷都由新增测试抓出，这也是本轮测试从 58 加到 62 个的原因。

## 六、实测不采用的适配项及理由

| 项 | 实测 | 结论 |
|---|---|---|
| B1 `QueryMultipleAsync` 压统计往返 | 同机对照 6.497 ms vs 7.285 ms，慢 12% | 多语句 SQL 的预处理开销超过省下的四次往返 |
| B3 单行路径改 JOIN | 同机对照 0.54 ms vs 0.61 ms，慢 13% | 三次主键直查有 6.4.1 的命令复用优化，比 25 列 JOIN 更快 |
| B2 `[Projection]` 直读 | 未实测即排除 | 浏览/搜索需要大部分列，投影只省一次对象构造；且 B3 已证明宽投影更慢 |
| B4 批量删除 | 未实测即排除 | 回收站永久删除不是热路径，且 Bulk 绕掉工作单元事务语义 |
| B5 `WithCache` 缓存 | 未实测即排除 | 所有端点已亚毫秒，收益低于一致性风险 |

三条共同的教训：**本地 SQLite 上"减少往返"不是有效优化方向**。
往返成本接近零，而预处理、宽结果集、投影物化都是真实成本。真正的收益来自
PalORM 编译期生成本身（对比 EF 的运行时开销）与版本内的命令复用优化。
