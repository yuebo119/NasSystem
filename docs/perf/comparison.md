# NAS 性能对比报告：net10+EF → net11+PalORM

## 一、报告定位

本文件是 .NET 11 + PalORM 迁移的**对比结论**，基线数据见 `baseline.md`。
三臂同机同轮采集，harness 与种子数据完全一致，唯一变量是目标框架与数据访问层。

| 臂 | 目标框架 | ORM | Git SHA | 角色 |
|---|---|---|---|---|
| A | .NET 10.0.12 | EF Core 10.0.12 | 0fad354 | 基线 |
| B | .NET 11.0.0-rc.1 | EF Core 10.0.12 | f71aa43 | 隔离运行时影响 |
| C | .NET 11.0.0-rc.1 | PalORM 6.1.0 | 97e35a0 | 目标态 |

机器：DESKTOP-IDCGOGO，Windows NT 10.0.19045.0，32 逻辑核。种子：10,000 行 FileItems。
原始记录：`docs/perf/net10-ef-20261011-18{4714,5025,0829}`、`net11-ef-20261011-{191741,192105,192618}`、
`net11-palorm-20261011-{201157,201550,202058}`。

## 二、收益归因

| 指标 | A (net10+EF) | B (net11+EF) | C (net11+PalORM) | A→B 运行时 | B→C ORM | A→C 合计 |
|---|---:|---:|---:|---:|---:|---:|
| API 吞吐 (req/s) | 4,718 | 4,470 | 13,944 | −5.3% | +212% | +196% |
| API P50 (ms) | 1.01 | 1.14 | 0.54 | +12.9% | −52.6% | −46.5% |
| API P99 (ms) | 8.13 | 8.03 | 1.17 | −1.2% | −85.4% | −85.6% |
| 冷启动中位 (ms) | 1,151 | 1,076 | 566 | −6.5% | −47.4% | −50.8% |
| 稳态工作集 (MB) | 105 | 107 | 86 | +1.9% | −19.6% | −18.1% |
| Release 发布体积 (MB) | 380 | 380 | 411 | 0% | +8.2% | +8.2% |

**结论一：运行时升级（net10 → net11）对这个负载基本没有影响。** B 臂与 A 臂的差距都在
5% 到 13% 区间，且 API 吞吐略降、延迟略升，方向不一致，属于测量噪声量级。
本项目的瓶颈从头到尾不在运行时。

**结论二：几乎全部收益来自换 ORM。** B→C 一段 API 吞吐提升 212%，P99 下降 85%，
冷启动减半。EF Core 的运行时开销（变更追踪、表达式树翻译、模型构建）是这个项目的主要成本。

**结论三：发布体积是唯一变差的指标**（+31 MB）。PalORM.Sqlite 拉入 SQLite3MC 原生包，
为多平台各带一份 native 二进制。对部署形态是 Docker 镜像增大的实际代价。

## 三、数据访问层逐项对比（P50，毫秒）

| 用例 | A: net10+EF | B: net11+EF | C: net11+PalORM | C 相对 A | C 相对 ADO.NET 地板 |
|---|---:|---:|---:|---:|---:|
| GetByPath | 0.142 | 0.163 | 0.041 | −71% | 2.15× |
| GetChildren | 1.495 | 1.454 | 1.558 | +4% | 1.64× |
| Search 名称模糊 | 3.740 | 3.757 | 2.581 | −31% | 0.61× |
| GetStatistics | 11.792 | 11.772 | 6.558 | −44% | 0.62× |
| GetDescendants | 3.426 | 3.419 | 1.572 | −54% | 0.42× |
| GetPagedUsers | 0.145 | 0.146 | 0.059 | −59% | 1.89× |
| CalculateUserUsedSpace | 0.076 | 0.075 | 0.025 | −67% | 1.07× |
| PathExists | 0.049 | 0.047 | 0.011 | −78% | 1.24× |
| GetByStoragePool | 7.622 | 7.609 | 6.000 | −21% | 1.04× |
| GetDeletedItems | 3.346 | 3.318 | 1.717 | −49% | 1.70× |
| CalculateStoragePoolUsedSpace | 1.814 | 1.812 | 0.396 | −78% | 0.18× |
| Insert 20 行（写） | 4.423 | 4.760 | 0.717 | −84% | 0.20× |
| Update 20 行（写） | 0.661 | 0.660 | 0.364 | −45% | 0.12× |
| Delete 20 行（写） | 4.514 | 4.554 | 1.304 | −71% | 0.31× |

三点值得单独说：

- **收益最大的是写入。** Insert 从 4.42 ms 降到 0.72 ms（−84%），Delete −71%。
  EF 每次 SaveChanges 要跑变更检测与命令批处理；PalORM 的意图队列直接按登记顺序下发，
  且 GUID 主键无需回读自增值。
- **GetStatistics 仍是最重单点**（6.56 ms），但已从 11.79 ms 降了 44%。
  它一次发 5 条聚合 SQL 加 1 条分组，成本主要在 SQLite 服务端。
- **GetChildren 是唯一没有改善的读用例**（+4%）。它返回约 50 行并构造领域对象，
  成本由物化与对象构造主导，ORM 翻译的占比本来就小。

## 四、API 端到端逐端点对比（P50 / P99，毫秒）

| 端点 | A: net10+EF | C: net11+PalORM | P50 变化 |
|---|---|---|---:|
| `/api/v1/system/health` | 0.27 / 0.84 | 0.34 / 0.82 | +26% |
| `/api/v1/storage/overview` | 0.82 / 1.86 | 0.59 / 1.15 | −28% |
| `/api/v1/users` | 0.81 / 2.01 | 0.61 / 1.25 | −25% |
| `/api/v1/file-shares` | 1.37 / 2.98 | 0.64 / 1.25 | −53% |
| `/api/v1/files/search` | 1.07 / 2.34 | 0.67 / 1.27 | −37% |
| `/api/v1/files/statistics` | 1.37 / 2.98 | 0.50 / 1.05 | −64% |
| `/api/v1/files/browse/*` | 5.82 / 9.31 | 0.55 / 1.12 | −91% |

`/files/browse` 改善最显著：EF 时代它要取目录内容并组装列表（P50 5.82 ms），
换成 PalORM 后掉到 0.55 ms。`/system/health` 是唯一变差的端点（0.27 → 0.34 ms），
但它本身只做探活，绝对值在 0.3 ms 量级，且与数据层无关，归入噪声。

## 五、口径与已知限制

- 绝对值仅在本机本轮有效；三臂同机同 SDK 同种子，比值可比。
- 数据访问层不含 DI 与 HTTP 管线；端到端差异看第四节。
- 地板臂为裸 ADO.NET 等价 SQL，不构造领域对象。C 臂多个用例快过地板，
  原因是 PalORM.Sqlite 连接级自动调优 8 项 PRAGMA（cache_size 64MB、temp_store MEMORY、
  mmap_size 256MB 等），而地板臂只设了 busy_timeout 与 synchronous 两项。
  这不说明 PalORM 比手写 SQL 快，只说明它的连接配置更全。
- 发布体积增大来自 SQLite3MC 多平台原生包，未做裁剪。
- .NET 11 仍是 RC1（SDK 11.0.100-rc.1.26425.128）。GA 后需重跑一轮确认数字仍成立，
  预计只需 bump `global.json` 版本号。
- `dotnet test` 的 MTP 宿主集成在本机是坏的（存量问题，已用 stash 对照验证）；
  直接跑测试可执行文件则 148 单元 + 54 集成全部通过。
